# Reading List & Ingestion

Luna is a weblink reader: links saved from Safari (extension + intent) or pasted in-app are downloaded, stripped to readable text, and read in two reader modes.

## Surface list presentation

Luna Reader and Luna Price Tracker do not show the shared "Reading List" title on
their home screens. An empty Reader explains how to save reading material; an empty
Price Tracker prompts the user to track a product. Reader's active items and Price
Tracker's active/alerting trackers render without a section header, while Reader's
Archive section keeps its header and controls.

> **Note:** the reader-shared models + ingest helpers moved to `ReaderKit/`
> (shared with the LunaShare target): `ReadingListItem`, `ReadingListStore`,
> `ArticleContent`, `ArticleFetcher`, `ArticleExtractor`. Paths below that say
> `Luna/ReadingList/...` for those files now live under `ReaderKit/`. See
> `readers.md`.

## Key files

- `ReaderKit/ReadingListItem.swift` — model. Content state: `pending → ready | failed | needsCaptcha` (failed retries on launch/foreground/pull-to-refresh; `needsCaptcha` is a hard-paywall holding state — see **Hard paywalls** below — that only the user can advance, so it is NOT retried by `ingestAllPending`). Read state: `unopened → opened → read` (never downgrades). `archivedAt` moves Reader items out of the carousel into its right-edge archive tray without removing content. Archiving calls `PreloadStore.releaseTree(rootID:)`, so the save keeps its complete article/original artifacts but owns no recursive preloads (effective depth 0); unarchiving does not automatically rebuild the tree. `lastReaderMode` remembers scroll vs rsvp per article. Decoding defaults `readState` and archive state for pre-existing items. Scroll/word position writes remain asynchronous during ordinary reader teardown, but the RabbitHole host drains them synchronously on `didEnterBackground` so a force-quit cannot lose the latest position before a cold launch.
- The Reader carousel keeps completed articles as ordinary live-reader cards for
  now, sorted after every unopened/in-progress card (newest/bumped-first within
  each group). Completed cards start at the article opening instead of restoring
  their terminal footer offset; unfinished cards restore their exact saved
  scroll position.
- `ReaderKit/ReadingListStore.swift` — JSON persistence in the App Group container (`group.com.hsanabria.luna`): `readingList.json` + `Articles/<uuid>.json` per article. Shared with the intent process. Posts `Notification.Name.readingListChanged` on every mutation. Reads disk fresh per call (simple over fast). Mutations are TARGETED (setLastWordIndex/markFailed/markReadState/setReaderMode/saveContent fetch fresh and set single fields) — whole-item writes from stale copies silently reverted other screens' fields. **Cross-process safety**: every read-modify-write runs inside a single `NSFileCoordinator` writing coordination via `coordinatedMutate`/`coordinatedUpdate` (and the share/action extension's `SharedReadingListAppender` coordinates too), so the app, SaveLink intent, and extensions can't lose each other's writes. File deletes go through `removeFiles(for:)` using `ReadingListItem.sanitizedDocumentType`.
- `Luna/ReadingList/ReadingListIngestor.swift` — fetch + extract orchestration; dedupes in-flight IDs; `ingestAllPending()` runs at launch/foreground. `handleSavePress(urlString:)` is the save entry point for intents and the in-app add: new URL saves+ingests, a repeat press within 12 s may send to Kindle (see `send-to-kindle.md`), any other repeat press is ignored. After successful `saveContent`, notifies `ArticleSendCoordinator.articleBecameReady`. New-save automation (auto-share to always-friends `fireAutoShares` + `armSemanticSuggestionIfNeeded`) is factored out and shared with `saveNewWithContent(urlString:content:)` — the latter persists already-fetched content directly (used by the pasteboard suggestion so tapping opens instantly without re-fetching).
- **News-aggregator unwrapping** (`ReaderKit/NewsAggregatorUnwrapper.swift`): the FIRST thing `ingest` does is unwrap a wrapper URL to the real publisher article — a wrapper breaks BOTH extraction (the aggregator page is a JS shell) and the archive flow (archive.today can't snapshot it). `NewsAggregatorUnwrapper.unwrap(_:)` (async; returns nil after a cheap host check for non-wrappers, so no network for ordinary URLs) handles: **Apple News** (`apple.news`) — fetch the page, parse the `redirectToUrlAfterTimeout("<url>")` JS call (its `og:url`/canonical point at apple.news itself; News+ exclusives have no underlying URL → nil); **Google News** (`news.google.com`) — offline base64-decode of the classic `CBMi…` article id (the blob embeds the publisher URL as a substring), falling back to Google's internal `batchexecute` RPC for new-style ids; **link shorteners** (`t.co`, `nyti.ms`, `flip.it`, …) — HEAD-follow the redirect to the final cross-host URL; **Facebook redirects** (`facebookRedirectTarget`, pure/offline — the target travels inline): `fbrpc://…/f?…&target_url=…` deep links (shared out of the FB app, read `target_url`) and `l.facebook.com`/`lm.`/`m.`/`facebook.com` `/l.php?u=…` link shims (read `u`), returning the percent-decoded http(s) target on a non-Facebook host (the `fbrpc` check runs BEFORE the http-host gate since the deep link has no http host; `fbclid` is then dropped by `ArticleFetcher.canonicalForArchiving`). Since Stage 3, the unwrap CHOKE POINT is `URLUnwrapper.unwrap` (the extensible `[WrapperHandler]` registry over these pure parsers), run ONCE at the top of `IngestPipeline.process` on EVERY surface (and once more in `ingest` to repoint the store via `store.updateURL`, dropping the item if the unwrapped article is already listed — the pipeline re-unwrap is then idempotent). Pure parsing is unit-tested (`NewsAggregatorUnwrapperTests` + `URLUnwrapperTests`); a hard-paywall publisher behind a wrapper (e.g. `nyti.ms` → nytimes.com) routes to the archive CAPTCHA as usual. **fbrpc entry-point gate**: an `fbrpc://` deep link has no http scheme, so a SAVE ENTRY POINT's `hasPrefix("http")` input gate would drop it before the pipeline runs. `URLUnwrapper.unwrapOffline(_:)` (sync/pure — resolves the offline handlers: Facebook deep link/shim + classic Google News) applies it up front at `ShareViewController.handleURL` / `handleJavaScriptResult` / `handleFriendShare`, the in-app `ReadingListViewController` Save-a-Link alert (via `normalizedTypedURL`, which ALSO validates the scheme — no more blind `https://` prefix), and every app intent via `IntentIngestHelper.handleSavePressWithTimeout`. (`NewsAggregatorUnwrapper.facebookRedirectTarget`/`normalizedIncomingURL*` remain as pure parsers/test-covered shims behind `URLUnwrapper`.)
- **Platform items**: the pipeline's `Classifier` recognizes a platform URL (X/Bluesky/Reddit/TikTok/IG/FB/Spotify/Apple) BEFORE any fetch — `Outcome.social`/`.video`/`.audio` → `IngestorOutcomePresenter` routes to `ingestPlatformItem`/`handleVideo` → `.ready` no-content item, NEVER `.failed` or text-extracted. Rendering still goes through `PlatformRegistry.module(for:)`. `ReadingListItem` gains `platform`/`platformItemID`/`mediaCreatorName`/`mediaItemTitle`/`mediaSourceService`. See `content-platforms.md`.
- `ReaderKit/ArticleFetcher.swift` — `URLSession` GET, Googlebot UA first (soft-paywall bypass: crawler UA + no JS), Safari UA fallback. `fetchArchivedHTML(for:)` is the hard-paywall fallback: tries the **Wayback Machine** (`archive.org/wayback/available` → replay snapshot; automation-friendly, no CAPTCHA) then **archive.today** (`archive.ph/newest/<url>`; user-submitted snapshots that bypass more paywalls but rate-limit/CAPTCHA datacenter IPs with HTTP 429).
- **Shared pipeline** (`ReaderKit/IngestPipeline.swift`): `IngestPipeline.process(_ input: IngestInput, timeout:…, …) async -> Outcome` is the SINGLE entry every surface calls. `IngestInput` = `url` + `source: CaptureSource` + optional `documentType`/`prefetchedHTML`/`forceArticle`. `Outcome` (EXHAUSTIVE): `.article(content, html:)` | `.product(ProductInfo, html:)` | `.social(platform, itemID:)` | `.video(platform, itemID:)` | `.audio(platform, service:, itemID:)` | `.document(type:)` | `.needsArchive(title:)` | `.failed`. Order: `URLUnwrapper.unwrap` ONCE → `Classifier.classify` (platform/video/audio/document FIRST, before any fetch) → per-kind processing — all wrapped in ONE overall timeout (`processTimeout = 28s`) so it can never hang (on timeout → `.needsArchive` for a hard-paywall host, else `.failed`). Deterministic news classifications are authoritative in both ingestion and `BypassGate`: known free/paywalled publishers skip heuristic product detection, preventing embedded store cards, subscription offers, or generic commerce component state from recategorizing the primary article or suppressing its unlock plan (the New Yorker regression); known shops remain trusted products and only `.undetermined` pages use product heuristics. A title-less background-fetch rejection also becomes `.needsArchive` when the selected `BypassPlan` has a browser pre-stage: this is how Reuters' DataDome `401` reaches its direct-unlock WKWebView/script-blocking rule instead of being terminally marked failed before the browser tier runs. Unknown hosts with no browser recovery remain `.failed`. Identical for the main-app ingestor AND both share-sheet extensions + intents + friend receive; they differ only in their `OutcomePresenter`. `render` defaults nil (extension-safe — no WebView); the main app injects `WebViewPriceRenderer`. Dep-free (compiles in the extensions). See `readers.md`. Tests: `IngestPipelineTests` + `OutcomePresenterTests`. (Replaces the deleted `ArticleIngestDecider`.)
- **Safari parity:** `LunaSafari/Resources/content.js` consumes the generated shared news-host table before deciding which pill to show. Known news publishers therefore skip Safari's product heuristic too, so publisher commerce/subscription furniture cannot produce a “Track in Luna” pill. With on-device unlock enabled, the generic cleanup removes content-less paywall overlays and unhides article nodes carrying the `paywall` class (the New Yorker full-body shape), allowing the article to unlock in place before “Read in Luna” captures the rendered HTML.
- `ReaderKit/ArticleResolver.swift` — `ArticleResolver.resolve(url:prefetchedHTML:)` → `ArticleResolution` (`.readable(content, html:)` | `.paywalled(title:)` | `.unreadable`). Called by `IngestPipeline`'s web-processing branch; `prefetchedHTML` reuses the product-detection fetch. Tries the direct fetch, then `fetchArchivedHTML`; returns readable content from either, else the best non-placeholder title found — preferring the direct page's title (FT serves a titled subscription stub), falling back to the archive snapshot's (WSJ 401s with no title directly, but its Wayback snapshot still carries one) — so a paywalled item can be labeled and parked in `.needsCaptcha`. Pure decision split into `resolution(direct:archived:)` (unit-tested, `ArticleResolverTests`). The archive.today URLSession leg uses a short 12s timeout (it almost always CAPTCHAs → fall through fast, don't stall the share sheet).
- `ArticleContent.hasReadableBody` = ≥1200 chars of block text AND `!looksPaywalled`. **`looksPaywalled`** = high-precision gate phrases at any length (`to continue reading`, `subscribe to read`, …), or weaker subscription-marketing phrases only in a SHORT body (<2500 chars: `try unlimited access`, `complete digital access`, `cancel anytime`, `subscriber agreement`, `personal, non-commercial use`, …). HTML-level locks (`isAccessibleForFree:false`, premium/metered `article:content_tier`) also reject only short/teaser-shaped bodies; long gate-free article prose wins even if the publisher labels it subscriber-only (New Statesman-style full HTML). This catches BOTH the FT marketing interstitial and the WSJ Wayback teaser while avoiding archive fallback for complete subscriber-marked responses. Tested in `ArticleContentPaywallTests`, `PaywallDetectorTests`, and `ArticleExtractionTests`.
- **Hard paywalls** (`needsCaptcha`): when `ArticleResolver` gets a title but no readable body, the ingestor calls `store.markNeedsCaptcha` → state `.needsCaptcha`, shown in the list with a **lock** thumbnail + **"tap to unlock"** subtitle. Tapping opens `ReaderKit/ArchiveWebReaderViewController` — a `WKWebView` loaded to `archive.ph/newest/<url>` (URL pre-filled in the PATH, so the user never types it). archive.today gates many clients behind a **Cloudflare reCAPTCHA** that issues a `cf_clearance` cookie **bound to the exact User-Agent**; the view sets a fixed real-mobile-Safari `customUserAgent` (the default WKWebView UA omits the `Safari/` token → Cloudflare re-challenges after every solve = the infinite-CAPTCHA loop) and uses the persistent `.default()` cookie store (one solve unlocks later articles too). `isChallengePage` (detects `/cdn-cgi/l/chk_captcha`) prevents extracting the challenge page. **archive.today rate-limits by IP with HTTP 429 and won't honor CAPTCHA solves until it cools (device logs confirmed: the UA fix is live but solving still 429-loops — it's an IP/network block on the only full-text source, not a webview bug, and not client-side-fixable).** So after `challengeCount >= 3` consecutive 429s the view hides the dead challenge and shows **actionable guidance** (wait ~30 min / switch network or VPN / open in Safari with content blockers disabled — Safari passes the CAPTCHA, blocked only by the user's ad blocker). A **Safari escape-hatch** button (`onOpenInBrowser`, main-app-only) opens the archive URL in real Safari. Per-step `SharedDiagnosticLog` lines (`[archive] …`, incl. per-main-frame `navAction type=`) make on-device loops self-diagnosing. Once a real snapshot loads (`innerText.length > 1500`, not a challenge page) it extracts the article off the DOM and `saveContent` flips it to `.ready`. `onClose`/`onExtracted` injectables let extensions complete their request / show a checkmark.
- `Luna/ReadingList/ArticleExtractor.swift` — SwiftSoup mini-readability: strips `script/style/nav/header/footer/aside/form/iframe/svg/button`, scores parents by direct `<p>` text length, emits ordered blocks (`paragraph|heading|quote|listItem|image`) with UTF-16 inline link ranges, plus `author`. LAYERED, never fails while any text exists: refined (junk class/role stripping + trailing link-farm trimming; used only when ≥350 chars AND ≥1/3 of basic) → basic (structural-tag stripping only) → JSON-LD `articleBody` override (when it dwarfs the DOM result — React sites ship the article as metadata) → raw body text. Container scoring credits ancestors with decaying weight (readability-style) so per-paragraph div wrappers still resolve to the article container; the winner is then WIDENED upward until it covers ≥60% of the document's paragraph text (CMSs that split the body across sibling slice containers, e.g. itsnicethat).
- `Luna/ReadingList/ArticleContent.swift` — extracted content model (blocks + link ranges).
- **Price tracking** (`claudedocs/price-tracking.md`): a saved/pasted URL that is a product page with a price becomes a **price tracker** (watch N store URLs, alert on a price drop) instead of an article. Product detection runs inside `IngestPipeline`'s web-processing branch (after the platform/video/audio classification, before the article resolve); an `Outcome.product` routes to `ingestProductTracker` (intelligent merge via `ProductMatcher`, else new tracker). Adds `ReadingListItem.priceTracker: PriceTracker?`, a `.priceTracking` section (which sits **below** Reading in `displayOrder`) + a `.priceTrackers` filter segment to `ReadingListSectioning`, a `PriceTrackingViewController` editor (push-only; Done/Cancel both exit), a `com.hsanabria.luna.priceRefresh` BGProcessingTask, and a `MessageBody.priceTracker` friend-share variant. A tracker whose price has dropped past threshold AND not yet been viewed floats as the single red-badged row of the **`.priceAlert`** section at the very top of the whole list (`topUnviewedAlertingPriceTracker`); opening it marks the alert viewed (`PriceTracker.markAlertViewed`) so it rejoins the price-tracking section below Reading.
- `Luna/ReadingList/ReadingListSectioning.swift` — **pure** (UIKit-free, unit-tested) sectioning logic extracted from the VC: `Section`/`ListFilter` enums (stable raw values 0/2/3/4/5), `assignSections(items:now:)` (Reading/Archive/Error buckets, 7-day `archiveAge` strict-`>` cutoff), `shouldShowFilter(items:)`, `rendersAsReader(_:)`. The VC delegates to these.
- `Luna/ReadingList/ReadingListSubtitle.swift` — **pure** assembly of the grey metadata line: `parts(for:leadingLabel:formattedDate:showReadingTime:showReadingProgress:)` → ordered `[String]` (leading label · date · reading time · progress% · send status · lifecycle status); `readingTimeMinutes(wordCount:)` = `ceil(words/220)` floored at 1. The VC builds the `NSAttributedString` (colors + "from <friend>") around these parts.
  - **Pasteboard suggestion**: the Reader and Downloader card roots use only
    `detectPatterns(.probableWebURL)` on launch/foreground and prepend a synthetic
    paste-icon card without reading the value. The actual read happens when the
    user pages onto that card. Reader resolves a full unsaved live reader and
    persists it when reading dismisses the carousel chrome. Downloader downloads
    into a one-hour temporary file, presents the real media paused, and persists
    to Luna + Photos on explicit Play (or a still-image tap). Both disappear if

- `Luna/ReadingList/SafariURLStore.swift` — reads `lastSafariURL`/`lastSafariURLDate` App Group defaults written by the LunaSafari extension.
  - **Hard paywalls in the extensions** (`ShareSurfaceDriver.presentArchive` + `ArchiveWebReaderViewController`, see `readers.md`): EVERY surface gets the same `Outcome` from the shared `IngestPipeline` and, on `.needsArchive`, marks `.needsCaptcha` and presents the SAME `ArchiveWebReaderViewController` directly (it used to wrap it in `ShareReaderViewController` only in the action ext — collapsed so the presentation intent matches the main app, enforced by `SurfaceParityTests`). The action ext swaps to the in-sheet native reader on extract; the share ext confirms. On `.failed` → the action ext shows an ERROR (never a misleading "Saved"), the share ext marks the item failed + completes quietly for the app to retry. Done completes the extension. The whole call is bounded by the pipeline's overall timeout, so the action extension can never spin forever.
- `LunaShare/` — share extension (`com.hsanabria.luna.share`, `NSExtensionPointIdentifier` = `com.apple.share-services`, activation: 1 web URL or 1 file). Uses `ShareKit` as principal class.
- `Luna Action Extension/` — action extension ("Read in Luna"; per-host bundle id `<host-app-bundle-id>.action2`, `NSExtensionPointIdentifier` = `com.apple.ui-services`, `NSExtensionPrincipalClass` = `$(PRODUCT_MODULE_NAME).ShareViewController`, activation: 1 web URL or 1 file). Same `ShareKit` code as the share extension; appears as a separate share-sheet action row and opens the reader (articles) or a playback/open-in-app screen (non-textual). Own App Group entitlement + per-surface transparent `ActionExtensionIcon*` template appiconset, generated by extracting and monochroming the actual foreground artwork from each 1024px `AppIcon*` master; links SwiftSoup; shares `ReaderKit` + `ShareKit` sync groups. **Ships `GetURL.js` + `NSExtensionJavaScriptPreprocessingFile`**: a `com.apple.ui-services` action extension gets no usable web URL from Safari without it — the URL arrives as the JS result in a `UTType.propertyList` attachment (`NSExtensionJavaScriptPreprocessingResultsKey` → `{URL,title}`), which `ShareViewController.handleJavaScriptResult` reads. `public.url`/file branches still cover non-Safari hosts.

## Failed saves

A `.failed` save shows a real error card on the Reader and Downloader card roots —
favicon + recovered title, the URL that failed, why it failed, a red rim, and
buttons for the LLM rescue / an in-app browser / sharing the link. It has no kind,
so it surfaces in EVERY app, and its menu offers Share Link + Delete only (no
Archive). Full design: `claudedocs/failed-saves.md`.

## Failed-save rescue (Apple Intelligence)

A `.failed` row is no longer a dead end: tapping it offers a one-shot LLM rescue
with a hint picker (Article / Price Tracker / Media Download), and — when the
"Failed Saves" setting is on — a background sweep retries failed items
automatically (2 attempts, 24h apart, tracked in the `rescueLedger.json` sidecar).
While a rescue runs, the row subtitle reads "trying harder…". Share/action
extensions can't run the LLM, so a failed extension save shows a "Finish in Luna"
card that hands off via `<scheme>://rescue` + the `PendingRescueRequestStore`
queue. Full design: `claudedocs/url-rescue.md`.
