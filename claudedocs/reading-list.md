# Reading List & Ingestion

Luna is a weblink reader: links saved from Safari (extension + intent) or pasted in-app are downloaded, stripped to readable text, and read in two reader modes.

> **Note:** the reader-shared models + ingest helpers moved to `ReaderKit/`
> (shared with the LunaShare target): `ReadingListItem`, `ReadingListStore`,
> `ArticleContent`, `ArticleFetcher`, `ArticleExtractor`. Paths below that say
> `Luna/ReadingList/...` for those files now live under `ReaderKit/`. See
> `readers.md`.

## Key files

- `ReaderKit/ReadingListItem.swift` — model. Content state: `pending → ready | failed | needsCaptcha` (failed retries on launch/foreground/pull-to-refresh; `needsCaptcha` is a hard-paywall holding state — see **Hard paywalls** below — that only the user can advance, so it is NOT retried by `ingestAllPending`). Read state: `unopened → opened → read` (never downgrades). `lastReaderMode` remembers scroll vs rsvp per article. Decoding defaults `readState` for pre-existing items.
- `ReaderKit/ReadingListStore.swift` — JSON persistence in the App Group container (`group.com.hsanabria.luna`): `readingList.json` + `Articles/<uuid>.json` per article. Shared with the intent process. Posts `Notification.Name.readingListChanged` on every mutation. Reads disk fresh per call (simple over fast). Mutations are TARGETED (setLastWordIndex/markFailed/markReadState/setReaderMode/saveContent fetch fresh and set single fields) — whole-item writes from stale copies silently reverted other screens' fields. **Cross-process safety**: every read-modify-write runs inside a single `NSFileCoordinator` writing coordination via `coordinatedMutate`/`coordinatedUpdate` (and the share/action extension's `SharedReadingListAppender` coordinates too), so the app, SaveLink intent, and extensions can't lose each other's writes. File deletes go through `removeFiles(for:)` using `ReadingListItem.sanitizedDocumentType`. **Search**: see `search.md` — the top-right magnifyingglass opens a full-screen search (string + semantic) reusing these rows.
- **Backup/restore policy**: user-owned state is backup-visible: `readingList.json`, `Articles/`, `OriginalArchives/`, `RabbitHole/`, friends/pending/recents JSON, and app-group `UserDefaults` metadata stay eligible for iCloud/device backups. Rebuildable or diagnostic data is explicitly excluded with `BackupPolicy`: `Preloads/`, `semanticIndex.json`, `clip-diagnostics.log`, replay zips, temp media downloads, and live-download working files. Credential secrets (email account, Boox, YouTube OAuth) live in migratable + `kSecAttrSynchronizable` Keychain items via `CredentialKeychain`, so encrypted device restores and iCloud Keychain can preserve them when the user has those system features enabled.
- **Replays** (`claudedocs/replays.md`): `ingest` begins a diagnostic `Replay` per save (covering intents/paste/manual via the single `ingest` seam), wraps the resolver fetcher with `RecordingHTMLFetcher` to capture every request/response, records the unwrap/resolve/extraction decisions, and terminates on the outcome. The share/action extensions and the archive web reader record their own replays too. Diagnostics → Replays lists them; a "Report a bug" action (reading-list long-press menu + the reader footer's bug icon) marks one `.userReported` and shares its zip.
- `Luna/ReadingList/ReadingListIngestor.swift` — fetch + extract orchestration; dedupes in-flight IDs; `ingestAllPending()` runs at launch/foreground. `handleSavePress(urlString:)` is the save entry point for intents and the in-app add: new URL saves+ingests, a repeat press within 12 s may send to Kindle (see `send-to-kindle.md`), any other repeat press is ignored. After successful `saveContent`, notifies `ArticleSendCoordinator.articleBecameReady`. New-save automation (auto-share to always-friends `fireAutoShares` + `armSemanticSuggestionIfNeeded`) is factored out and shared with `saveNewWithContent(urlString:content:)` — the latter persists already-fetched content directly (used by the pasteboard suggestion so tapping opens instantly without re-fetching).
- **News-aggregator unwrapping** (`ReaderKit/NewsAggregatorUnwrapper.swift`): the FIRST thing `ingest` does is unwrap a wrapper URL to the real publisher article — a wrapper breaks BOTH extraction (the aggregator page is a JS shell) and the archive flow (archive.today can't snapshot it). `NewsAggregatorUnwrapper.unwrap(_:)` (async; returns nil after a cheap host check for non-wrappers, so no network for ordinary URLs) handles: **Apple News** (`apple.news`) — fetch the page, parse the `redirectToUrlAfterTimeout("<url>")` JS call (its `og:url`/canonical point at apple.news itself; News+ exclusives have no underlying URL → nil); **Google News** (`news.google.com`) — offline base64-decode of the classic `CBMi…` article id (the blob embeds the publisher URL as a substring), falling back to Google's internal `batchexecute` RPC for new-style ids; **link shorteners** (`t.co`, `nyti.ms`, `flip.it`, …) — HEAD-follow the redirect to the final cross-host URL; **Facebook redirects** (`facebookRedirectTarget`, pure/offline — the target travels inline): `fbrpc://…/f?…&target_url=…` deep links (shared out of the FB app, read `target_url`) and `l.facebook.com`/`lm.`/`m.`/`facebook.com` `/l.php?u=…` link shims (read `u`), returning the percent-decoded http(s) target on a non-Facebook host (the `fbrpc` check runs BEFORE the http-host gate since the deep link has no http host; `fbclid` is then dropped by `ArticleFetcher.canonicalForArchiving`). Since Stage 3, the unwrap CHOKE POINT is `URLUnwrapper.unwrap` (the extensible `[WrapperHandler]` registry over these pure parsers), run ONCE at the top of `IngestPipeline.process` on EVERY surface (and once more in `ingest` to repoint the store via `store.updateURL`, dropping the item if the unwrapped article is already listed — the pipeline re-unwrap is then idempotent). Pure parsing is unit-tested (`NewsAggregatorUnwrapperTests` + `URLUnwrapperTests`); a hard-paywall publisher behind a wrapper (e.g. `nyti.ms` → nytimes.com) routes to the archive CAPTCHA as usual. **fbrpc entry-point gate**: an `fbrpc://` deep link has no http scheme, so a SAVE ENTRY POINT's `hasPrefix("http")` input gate would drop it before the pipeline runs. `URLUnwrapper.unwrapOffline(_:)` (sync/pure — resolves the offline handlers: Facebook deep link/shim + classic Google News) applies it up front at `ShareViewController.handleURL` / `handleJavaScriptResult` / `handleFriendShare`, the in-app `ReadingListViewController` Save-a-Link alert (via `normalizedTypedURL`, which ALSO validates the scheme — no more blind `https://` prefix), and every app intent via `IntentIngestHelper.handleSavePressWithTimeout`. (`NewsAggregatorUnwrapper.facebookRedirectTarget`/`normalizedIncomingURL*` remain as pure parsers/test-covered shims behind `URLUnwrapper`.)
- **Platform items**: the pipeline's `Classifier` recognizes a platform URL (X/Bluesky/Reddit/TikTok/IG/FB/Spotify/Apple) BEFORE any fetch — `Outcome.social`/`.video`/`.audio` → `IngestorOutcomePresenter` routes to `ingestPlatformItem`/`handleVideo` → `.ready` no-content item, NEVER `.failed` or text-extracted. Rendering still goes through `PlatformRegistry.module(for:)`. `ReadingListItem` gains `platform`/`platformItemID`/`mediaCreatorName`/`mediaItemTitle`/`mediaSourceService`. See `content-platforms.md`.
- `Luna/ReadingList/PasteboardSuggester.swift` — `PasteboardSuggesting.evaluate(urlString:)` → `PasteboardCandidate?`. Off the main thread: FIRST runs `URLUnwrapper.unwrapOffline` (so a Facebook `fbrpc://…&target_url=http…` deep link on the pasteboard unwraps to its real http target before the http-scheme gate — IDENTICAL to the "+" `addTapped` path; this fixes the bug where a pasted Facebook link failed while the same URL via "+" succeeded), then dedupes against the store, detects YouTube (oEmbed metadata → video candidate) else fetches + extracts the article (→ candidate carrying the extracted `ArticleContent` for instant open). Returns nil for still-non-http URLs (after unwrap), already-saved URLs, or nothing extractable. Protocol + mock + tests (`PasteboardSuggesterTests`).
- `ReaderKit/ArticleFetcher.swift` — `URLSession` GET, Googlebot UA first (soft-paywall bypass: crawler UA + no JS), Safari UA fallback. `fetchArchivedHTML(for:)` is the hard-paywall fallback: tries the **Wayback Machine** (`archive.org/wayback/available` → replay snapshot; automation-friendly, no CAPTCHA) then **archive.today** (`archive.ph/newest/<url>`; user-submitted snapshots that bypass more paywalls but rate-limit/CAPTCHA datacenter IPs with HTTP 429).
- **Shared pipeline** (`ReaderKit/IngestPipeline.swift`): `IngestPipeline.process(_ input: IngestInput, timeout:…, …) async -> Outcome` is the SINGLE entry every surface calls. `IngestInput` = `url` + `source: CaptureSource` + optional `documentType`/`prefetchedHTML`/`forceArticle`. `Outcome` (EXHAUSTIVE): `.article(content, html:)` | `.product(ProductInfo, html:)` | `.social(platform, itemID:)` | `.video(platform, itemID:)` | `.audio(platform, service:, itemID:)` | `.document(type:)` | `.needsArchive(title:)` | `.failed`. Order: `URLUnwrapper.unwrap` ONCE → `Classifier.classify` (platform/video/audio/document FIRST, before any fetch) → per-kind processing — all wrapped in ONE overall timeout (`processTimeout = 28s`) so it can never hang (on timeout → `.needsArchive` for a hard-paywall host, else `.failed`). Identical for the main-app ingestor AND both share-sheet extensions + intents + friend receive; they differ only in their `OutcomePresenter`. `render` defaults nil (extension-safe — no WebView); the main app injects `WebViewPriceRenderer`. Dep-free (compiles in the extensions). See `readers.md`. Tests: `IngestPipelineTests` + `OutcomePresenterTests`. (Replaces the deleted `ArticleIngestDecider`.)
- `ReaderKit/ArticleResolver.swift` — `ArticleResolver.resolve(url:prefetchedHTML:)` → `ArticleResolution` (`.readable(content, html:)` | `.paywalled(title:)` | `.unreadable`). Called by `IngestPipeline`'s web-processing branch; `prefetchedHTML` reuses the product-detection fetch. Tries the direct fetch, then `fetchArchivedHTML`; returns readable content from either, else the best non-placeholder title found — preferring the direct page's title (FT serves a titled subscription stub), falling back to the archive snapshot's (WSJ 401s with no title directly, but its Wayback snapshot still carries one) — so a paywalled item can be labeled and parked in `.needsCaptcha`. Pure decision split into `resolution(direct:archived:)` (unit-tested, `ArticleResolverTests`). The archive.today URLSession leg uses a short 12s timeout (it almost always CAPTCHAs → fall through fast, don't stall the share sheet).
- `ArticleContent.hasReadableBody` = ≥600 chars of block text AND `!looksPaywalled`. **`looksPaywalled`** = a SHORT body (<2500 chars) containing high-precision subscription-wall phrases (`try unlimited access`, `complete digital access`, `cancel anytime`, `subscriber agreement`, `personal, non-commercial use`, `to continue reading`, …). This catches BOTH the FT marketing interstitial (which clears 600 chars of marketing copy) AND the WSJ Wayback snapshot (which carries only the lede + one quote wrapped in Dow Jones boilerplate) — both are stubs/teasers, so they route to the archive instead of saving as "readable". Long real articles are never flagged. Tested in `ArticleContentPaywallTests`.
- **Hard paywalls** (`needsCaptcha`): when `ArticleResolver` gets a title but no readable body, the ingestor calls `store.markNeedsCaptcha` → state `.needsCaptcha`, shown in the list with a **lock** thumbnail + **"tap to unlock"** subtitle (and excluded from catch-up). Tapping opens `ReaderKit/ArchiveWebReaderViewController` — a `WKWebView` loaded to `archive.ph/newest/<url>` (URL pre-filled in the PATH, so the user never types it). archive.today gates many clients behind a **Cloudflare reCAPTCHA** that issues a `cf_clearance` cookie **bound to the exact User-Agent**; the view sets a fixed real-mobile-Safari `customUserAgent` (the default WKWebView UA omits the `Safari/` token → Cloudflare re-challenges after every solve = the infinite-CAPTCHA loop) and uses the persistent `.default()` cookie store (one solve unlocks later articles too). `isChallengePage` (detects `/cdn-cgi/l/chk_captcha`) prevents extracting the challenge page. **archive.today rate-limits by IP with HTTP 429 and won't honor CAPTCHA solves until it cools (device logs confirmed: the UA fix is live but solving still 429-loops — it's an IP/network block on the only full-text source, not a webview bug, and not client-side-fixable).** So after `challengeCount >= 3` consecutive 429s the view hides the dead challenge and shows **actionable guidance** (wait ~30 min / switch network or VPN / open in Safari with content blockers disabled — Safari passes the CAPTCHA, blocked only by the user's ad blocker). A **Safari escape-hatch** button (`onOpenInBrowser`, main-app-only) opens the archive URL in real Safari. Per-step `SharedDiagnosticLog` lines (`[archive] …`, incl. per-main-frame `navAction type=`) make on-device loops self-diagnosing. Once a real snapshot loads (`innerText.length > 1500`, not a challenge page) it extracts the article off the DOM and `saveContent` flips it to `.ready`. `onClose`/`onExtracted` injectables let extensions complete their request / show a checkmark.
- `Luna/ReadingList/ArticleExtractor.swift` — SwiftSoup mini-readability: strips `script/style/nav/header/footer/aside/form/iframe/svg/button`, scores parents by direct `<p>` text length, emits ordered blocks (`paragraph|heading|quote|listItem|image`) with UTF-16 inline link ranges, plus `author`. LAYERED, never fails while any text exists: refined (junk class/role stripping + trailing link-farm trimming; used only when ≥350 chars AND ≥1/3 of basic) → basic (structural-tag stripping only) → JSON-LD `articleBody` override (when it dwarfs the DOM result — React sites ship the article as metadata) → raw body text. Container scoring credits ancestors with decaying weight (readability-style) so per-paragraph div wrappers still resolve to the article container; the winner is then WIDENED upward until it covers ≥60% of the document's paragraph text (CMSs that split the body across sibling slice containers, e.g. itsnicethat).
- `Luna/ReadingList/ArticleContent.swift` — extracted content model (blocks + link ranges).
- `Luna/ReadingList/ReadingListViewController.swift` — home screen (insetGrouped), **FIFO** order within sections. Dynamic sections, top→bottom via `displayOrder` (decoupled from the enum raw values, which stay stable for the persisted collapsed set): **From Pasteboard** (one-tap suggestion, see below; always expanded), **Reading** (unread, saved <1 week, always expanded), **Archive** (read/archived items AND unread items older than a week — merged; collapsed by default, **Delete All** header button clears the whole section via `store.deleteItems(ids:)`), **Couldn't Load** (failed items, red header + red rows, collapsed by default, at the very bottom). Collapsible headers toggle on tap (chevron; collapsed set persisted in `readingListCollapsedSections`, defaults `[archive, error]`). Rows use a custom `ReadingListItemCell` (title + subtitle + a 96×54 thumbnail well). The thumbnail has three states: a **spinner** while the item is still being fetched (state `.pending`), the fetched **art** (decoded off-main, guarded by a reuse key; aspect-fit, switching to aspect-fill only when the ratio is beyond 2× the well's so the smaller dimension always fills ≥ half), or the **platform-logo fallback** (full-color favicon-derived PNG, or an SF glyph) once the fetch finished with no image. Articles attempt an `og:image`/`twitter:image` cover during ingest (`LeadImageExtractor`). The **From Pasteboard** row shows a spinner while the preview is fetched, then the candidate's resolved thumbnail (`PasteboardCandidate.thumbnail` — cover art / video still / platform art); tapping the row PREVIEWS it (transient, unsaved) and a trailing **Save** button (`plus.circle.fill`) saves it explicitly. Rows show host · date · reading time · progress %, plus **"from <friend>"** in the accent color (`secondaryAttributedText`); failed rows read in red and show "pull to retry". The pasteboard Save button is set as BOTH `accessoryView` and `editingAccessoryView` (the list can be editing, which hides the plain accessoryView). **Edit mode is on-demand** (no permanent handles): the long-press menu's bottom item **"Edit List"** calls `setEditing(true)` → selection radios (`allowsMultipleSelectionDuringEditing`), drag-anywhere reorder within Reading via `UITableViewDrag/DropDelegate` (no handle; persists `setOrder`, `isApplyingReorder`-guarded), and the top bar becomes (right→left) **Done / Select All / Delete Selected**; Done exits + clears. `didSelectRowAt` no-ops while editing (tap toggles the radio). Long-press menu (**Bump to Top** [Reading-section items only → `store.bump`] / Send to Friend / Send to Kindle / Send to Boox / Share Link / Copy Link / Download Media to Photos [X/Instagram/TikTok — see `media-download.md`] / Share eBook / **Unarchive** [archived/read items → `store.markUnread`] / Delete / **Edit List**) is suppressed for the pasteboard row; **Delete animates** via `deleteItemAnimated` (`deleteRows`/`deleteSections`, guarded by `isAnimatingRowChange`) instead of a full reload. `+` paste-a-URL alert, tap → ReaderViewController, pull-to-refresh retries failures. A header **Articles / Media & Links** segmented filter (`ListFilter`) shows only when the list has both kinds: *Articles* = anything that opens in the text reader (`rendersAsReader` — `contentPlatform == nil && !isYouTubeVideo`: articles, documents, emails); *Media & Links* = everything else (YouTube, platform posts, music/podcasts). Hidden (and reset to All) otherwise. A **catch-up** button (`rectangle.stack`, tinted `.label` like the other nav buttons — only the dot is red) is pinned to the "Reading List" large-title row (a nav-bar subview, re-pinned each `viewWillAppear`), with a red "action needed" dot when there are 10+ unread items; it opens the swipe-through catch-up experience (see `catch-up.md`) and is hidden in edit mode. Its alpha is tied DIRECTLY to how far the large-title bar has COLLAPSED — `updateCatchUpButtonFade` (in `scrollViewDidScroll`) measures `navigationBar.frame.height` shrinking from its observed peak and fades fully out within ~11pt of collapse, so the button is gone before it rises into the +/friends buttons, and returns when scrolled back to the top. (The bar height is the right signal because during a large-title collapse `adjustedContentInset.top` shrinks in lock-step with `contentOffset`, so `contentOffset+inset` stays ~0 and never reflects the collapse.) Overscrolling DOWN (pull-to-refresh) stretches the bar taller than its rest height — that's detected (`contentOffset.y < -adjustedContentInset.top`) and forced to alpha 1 WITHOUT inflating the peak, otherwise the bar would never match the inflated peak again and the button would stay hidden forever. `ReadingListStore.bump` re-sorts a bumped item to the top of the list. Media download (X/IG/TikTok) progress/result shows in a **non-blocking bottom pill** (`MediaDownloadStatusView`, `isUserInteractionEnabled=false`, a subview of the list so it never appears over the reader) and continues via a `beginBackgroundTask` if the app is backgrounded. The non-article open routing is factored into `openItem(_:presentingFrom:)` so catch-up can reuse it. SIMULATOR-ONLY: each cell has a bottom-left "Row actions" button (`setSimulatorMenu`, `AppEnvironment.isSimulator`) that opens the long-press menu on a plain tap (see `simulator-testing.md`).
- **Price tracking** (`claudedocs/price-tracking.md`): a saved/pasted URL that is a product page with a price becomes a **price tracker** (watch N store URLs, alert on a price drop) instead of an article. Product detection runs inside `IngestPipeline`'s web-processing branch (after the platform/video/audio classification, before the article resolve); an `Outcome.product` routes to `ingestProductTracker` (intelligent merge via `ProductMatcher`, else new tracker). Adds `ReadingListItem.priceTracker: PriceTracker?`, a `.priceTracking` section (which sits **below** Reading in `displayOrder`) + a `.priceTrackers` filter segment to `ReadingListSectioning`, a `PriceTrackingViewController` editor (push-only; Done/Cancel both exit), a `com.hsanabria.luna.priceRefresh` BGProcessingTask, and a `MessageBody.priceTracker` friend-share variant. A tracker whose price has dropped past threshold AND not yet been viewed floats as the single red-badged row of the **`.priceAlert`** section at the very top of the whole list (`topUnviewedAlertingPriceTracker`); opening it marks the alert viewed (`PriceTracker.markAlertViewed`) so it rejoins the price-tracking section below Reading.
- `Luna/ReadingList/ReadingListSectioning.swift` — **pure** (UIKit-free, unit-tested) section/catch-up logic extracted from the VC: `Section`/`ListFilter` enums (stable raw values 0/2/3/4/5), `assignSections(items:now:)` (Reading/Archive/Error buckets, 7-day `archiveAge` strict-`>` cutoff), `catchUpQueue(items:)` (unread + renderable, oldest-first by `bumpDate ?? dateAdded`), `shouldShowCatchUpDot(items:)` (≥10 unread OR an unread `needsCaptcha` save), `shouldShowFilter(items:)`, `rendersAsReader(_:)`. The VC delegates to these.
- `Luna/ReadingList/ReadingListSubtitle.swift` — **pure** assembly of the grey metadata line: `parts(for:leadingLabel:formattedDate:showReadingTime:showReadingProgress:)` → ordered `[String]` (leading label · date · reading time · progress% · send status · lifecycle status); `readingTimeMinutes(wordCount:)` = `ceil(words/220)` floored at 1. The VC builds the `NSAttributedString` (colors + "from <friend>") around these parts.
  - **Pasteboard suggestion**: on `didBecomeActive` (launch + every foreground) `checkPasteboard()` reads a clipboard URL — gated on `UIPasteboard.changeCount` so the system paste banner shows at most once per newly copied URL — and asks `PasteboardSuggester` whether it's readable. If so, `pasteboardCandidate` renders as a transient (unsaved) row under "From Pasteboard". Tapping `openPasteboardCandidate()` saves it (article: `saveNewWithContent` with the cached content; video: `handleSavePress`) and opens the reader/video; the row vanishes and the item lands in its normal section. Already-saved URLs are never suggested.
- `Luna/ReadingList/SafariURLStore.swift` — reads `lastSafariURL`/`lastSafariURLDate` App Group defaults written by the LunaSafari extension.
- `ShareKit/` — share-sheet logic shared by BOTH extension targets (sync folder group, member of `LunaShare` + `Luna Action Extension`). `ShareViewController` (plain zero-UI `UIViewController`): matches document types (pdf/rtf/text) BEFORE the generic `public.url` so shared PDFs (which also conform to a file-url) aren't dropped by the URL branch; `SharedReadingListAppender` appends a pending item to the App Group JSON (mirror `ReadingListItem` fields). For shared **plain text** and **.txt files**, `ShareKit/ShareTextURL.extract` first checks whether the text is really "just a link" — the whole thing is one URL plus whitespace/punctuation, OR it's short (≤200 chars) and starts with a URL — and if so imports only that URL, dropping the surrounding text. Also: (a) if launched from a Luna friend suggestion (`INSendMessageIntent`, conversation id = friend UUID), queues the URL via `pendingFriendShares.json` for the main app to send (see `social-sharing.md`); (b) the ingest+present flow is the host-agnostic **`ShareSurfaceDriver`** (`ShareKit/`), driven by an injected **`ExtensionHost`** protocol — `ShareViewController` is now just the real `ExtensionHost` adapter (attachment loading + live UIKit chrome). `ShareSurfaceDriver.ingestAndPresent(originalURL:)` runs the ONE `IngestPipeline.process`, repoints the store on unwrap, then `present(_:url:)` is an EXHAUSTIVE `Outcome` switch that PERSISTS the classified metadata for EVERY kind (so an extension save is shaped identically to a main-app save) and presents real UI: `.article` → `ShareReaderViewController` (action ext, `ExtensionReaderShareProvider` for end-of-article friend-share) or save+checkmark (share ext); `.video`/`.social`/`.audio` → `saveYouTubeMetadata`/`savePlatformMetadata` THEN `SavedNonTextualViewController` (action ext) or `autoDownloadThenComplete` (share ext) — fixes the bug where a YouTube link shared via the zero-UI share extension persisted only a bare URL; `.product` → save the tracker THEN present the SAME `PriceTrackingViewController` the main app shows, hosted in the extension via `PriceTrackingHost.extension` (Done chrome) — fixes the bug where the action extension saved a tracker silently with no price UI. The old divergent `ShareOutcomePresenter` is DELETED. `FakeExtensionHost` (`ShareSurfaceDriverTests` + `SurfaceParityTests`) drives the whole flow with no `NSExtensionContext`. See `readers.md`.
  - **Hard paywalls in the extensions** (`ShareSurfaceDriver.presentArchive` + `ArchiveWebReaderViewController`, see `readers.md`): EVERY surface gets the same `Outcome` from the shared `IngestPipeline` and, on `.needsArchive`, marks `.needsCaptcha` and presents the SAME `ArchiveWebReaderViewController` directly (it used to wrap it in `ShareReaderViewController` only in the action ext — collapsed so the presentation intent matches the main app, enforced by `SurfaceParityTests`). The action ext swaps to the in-sheet native reader on extract; the share ext confirms. On `.failed` → the action ext shows an ERROR (never a misleading "Saved"), the share ext marks the item failed + completes quietly for the app to retry. Done completes the extension. The whole call is bounded by the pipeline's overall timeout, so the action extension can never spin forever.
- `LunaShare/` — share extension (`com.hsanabria.luna.share`, `NSExtensionPointIdentifier` = `com.apple.share-services`, activation: 1 web URL or 1 file). Uses `ShareKit` as principal class.
- `Luna Action Extension/` — action extension ("Read in Luna"; `com.hsanabria.luna.Luna-Action-Extension`, `NSExtensionPointIdentifier` = `com.apple.ui-services`, `NSExtensionPrincipalClass` = `$(PRODUCT_MODULE_NAME).ShareViewController`, activation: 1 web URL or 1 file). Same `ShareKit` code as the share extension; appears as a separate share-sheet action row and opens the reader (articles) or a playback/open-in-app screen (non-textual). Own App Group entitlement + AppIcon; links SwiftSoup; shares `ReaderKit` + `ShareKit` sync groups. **Ships `GetURL.js` + `NSExtensionJavaScriptPreprocessingFile`**: a `com.apple.ui-services` action extension gets no usable web URL from Safari without it — the URL arrives as the JS result in a `UTType.propertyList` attachment (`NSExtensionJavaScriptPreprocessingResultsKey` → `{URL,title}`), which `ShareViewController.handleJavaScriptResult` reads. `public.url`/file branches still cover non-Safari hosts.
