# Audio Playback (Read-Aloud)

High-quality read-aloud for Luna Reader: offline-rendered speech through a
long-lived audio engine, background playback with Now Playing/remote
commands, a persistent mini-player, autoplay-next-article, and an
audio-specific trimming pass that speaks a cleaned-up subset of the visual
article text, extension-safe playback handoff, and a Siri/Spotlight surface —
this doc describes what exists now, not the phase-by-phase history (see git
log for that).

## Architecture

New SwiftPM module **`LunaAudioPlayback`** in `LunaLibraries/Package.swift`
(depends on `LunaModels`, `LunaAppConfig`, `LunaStorage`; `LunaReaderUI` and
`Luna/` depend on it). Swift 5 language mode, `public` API only.

### Render-to-buffer pipeline

- **`SpeechRenderer`** — offline synthesis via
  `AVSpeechSynthesizer.write(_:toBufferCallback:)`, normalizing every
  `AVAudioPCMBuffer` to one canonical float32 format with `AVAudioConverter`.
  Captures word timings from `willSpeakRangeOfSpeechString` during `write`,
  mapped to sample offsets. Output: `RenderedSegment { blockIndex, buffers,
  wordMarkers, duration }`.
- **`ArticleAudioEngine`** — long-lived `AVAudioPlayerNode` →
  `AVAudioUnitTimePitch` → `mainMixerNode`. User playback rate is
  `timePitch.rate` (rendered audio is never re-synthesized on a rate change).
  `SegmentRateMode.pinnedToNatural` locks a segment (announcements) to 1.0×
  regardless of the live rate, then restores it. Keeps ~2 rendered blocks
  ahead of the playhead (`maxBlocksAhead`). Tones (`ToneLibrary`,
  `ChimeTransition.caf`/`ChimeFinal.caf`, generated by
  `scripts/make_tones.py`) are scheduled on the same player node — no second
  audio session. Deliberately dumb: no article/queue concept, no
  `AVAudioSession` handling beyond what tests need.

### `AudioPlaybackCenter` (`LunaAudioPlayback/AudioPlaybackCenter.swift`)

App-wide singleton, single owner of playback. State machine: `idle /
playing(item) / announcing(next) / paused(item, resumable)`. One seam,
`weak var dataSource: AudioPlaybackCenterDataSource?` — nil by default (tests,
and the Share/Action extensions, never install one) so the module never
crashes when nothing is wired:

- `nextCandidate() -> QueueCandidate?` — the app shell's
  `AppAudioPlaybackDataSource` (installed by `Luna/AudioPlaybackWiring.swift`)
  resolves this to `AudioQueueRule.nextCandidate`: the top-most
  `readState == .unopened`, readable-article item in the current
  Reader-surface list order (reproduces `ReadingListSectioning`'s exact
  display order), excluding the currently-playing item. `.opened` items are
  never auto-queued (product decision). A nil `dataSource` means the autoplay
  chain finds no next candidate.
- `script(for:content:) -> AudioScript` — the same conformer forwards to
  `AudioScriptPipeline.shared.script(for:content:)`. `beginPlayback` falls
  back to `AudioScript(passthrough:)` (every non-empty block, verbatim) when
  `dataSource` is nil.
- `prefetch(item:content:)` — called when the autoplay chain resolves the
  NEXT queue candidate (before its chime/announcement even starts) so the
  script pipeline can verify/prefetch that item's script ahead of playback
  reaching it.

Autoplay chain on segment-queue completion: `store.markFinishedReading(id)` →
transition chime → "Now Reading — `<title>`" announcement (same voice, always
1.0×) → chime → next article's script; empty queue → final chime → `idle`.
Persists `(itemID, lastSpokenWordIndex, elapsedEstimate)` to App-Group
defaults (`AudioPlaybackPositionStore`) every ~5s while playing and on every
pause/seek, for cold-relaunch restore.

**Word-event contract:** `AudioWordEvent { blockIndex, rangeInBlockText }` is
always a range within the ORIGINAL `ArticleContent.Block.text` at
`blockIndex` — no re-mapping needed, because `AudioScript`/trimming only ever
*drops whole blocks*; a block that survives trimming keeps its source text
100% verbatim. Any future change to trimming must preserve this
whole-block-only contract, or reader word-highlighting breaks.

### System integration

- **`NowPlayingCoordinator`** — `MPNowPlayingInfoCenter` +
  `MPRemoteCommandCenter`, registered ONCE at app launch (required for
  background-relaunch command delivery — not lazy). `skipForwardCommand =
  [30]`, `skipBackwardCommand = [15]`, `changePlaybackPositionCommand`.
  Targets are re-asserted every time the center leaves `.idle` because the
  legacy `SpeechController` calls `removeTarget(nil)` on the same shared
  commands — see the file's "LEGACY-CONFLICT HANDOFF" comment.
- **`AudioSessionCoordinator`** — `.playback` + `.spokenAudio`, no mixing
  (spoken-audio semantics). Pauses without deactivating on interruption `.began`;
  resumes only if `.shouldResume` on `.ended`. `.oldDeviceUnavailable` route
  change pauses (keeps session active); `.newDeviceAvailable` (e.g. AirPods
  connecting) is a deliberate no-op — never auto-resumes. User pause
  schedules session deactivation after a 5s grace (`deactivationGrace`) with
  `.notifyOthersOnDeactivation`; Now Playing info + command targets stay
  registered the entire time (that registration, not session activity, is
  what keeps AirPods-press-to-resume working minutes later). Coexists with
  the legacy `LunaReaderUI.ReaderAudioSession` (extensions only).
- **`AudioSettings`** (`LunaAudioPlayback/AudioSettings.swift`) — App-Group
  UserDefaults: `isAutoplayEnabled` (default true, read fresh every autoplay
  boundary), `isIntelligentTrimmingEnabled` (default true), `preferredRate`
  (clamped to `rateSteps = [0.8, 1.0, 1.2, 1.5]`, shared with the legacy
  `SpeechController.cycleRate` menu).

### Trimming pipeline (`AudioScript*`/`AudioTrim*`)

- **`AudioScript`** — `{ spokenBlocks: [SpokenBlock { blockIndex, text }],
  totalWordCount, builderVersion }`. `passthroughBuilderVersion = 1`
  (Phase-1 stub, still a legitimate standing option — what "disable Apple
  Intelligence cleanup" falls back to). `heuristicBuilderVersion = 2` (current).
- **`AudioTrimHeuristics`** — deterministic, synchronous, always runs.
  Whole-block classification only. Drops image blocks, caption/credit
  patterns, high link-density blocks, related-link markers, social-embed
  boilerplate, share prompts. **Positional confidence:** a contiguous run
  from the article's start or end may be dropped on WEAK signals (bylines,
  datelines, "min read", newsletter signups); a MID-article block is only
  ever dropped on a HIGH-PRECISION signal (image blocks, exact caption
  patterns, explicit `READ MORE:`-style markers, very-high link density) —
  those same high-precision rules are also safe at the edges. **Global cap:**
  if the full rule set would drop >~50% of total word count
  (`globalCapFraction`), degrade to high-precision-only rules and report
  `didDegradeForGlobalCap`.
- **`AudioTrimIntelligence`** — optional, async, on-device FoundationModels
  refinement of the heuristic result. `@Generable AudioCleanupVerdict {
  removeIndices: [Int] }` — the model only ever returns block indices from a
  numbered list, never rewrites prose. Chunks surviving blocks ~25 at a time;
  `instructions` carries the task contract, `prompt` is only the numbered
  list (article text is never treated as instructions). Validates
  mechanically (in-range, unique, reject a chunk verdict flagging >50% of its
  blocks); positional rule applies to the LLM too (edge-adjacent removals
  accepted at face value, mid-article removals need a junk-category match).
  Errors degrade to heuristic-only: `guardrailViolation` → permanent for that
  article (never retried again); `exceededContextWindowSize` → halve chunk,
  retry once; `rateLimited` → skip this attempt; any parse failure → skip.
  Hidden behind `AudioTrimModelSession` protocol (`FoundationModelsTrimSession`
  vs. `UnavailableTrimSession`) so the orchestration is unit-testable with a
  fake — the real model is never available in a CI simulator, and every
  FoundationModels-importing type is `@available(iOS 26.0, *)`-guarded (see
  the deployment-target gotcha below).
- **`AudioScriptStore`** — persists the finished `AudioScriptCacheEnvelope
  { script, refined, llmPermanentlyFailed }` as `<contentFileName-stem
  >.audioScript.json`, sibling to the item's content file in
  `ReadingListStore.articlesDirectory`. Excluded from backups
  (`BackupPolicy.excludeFromBackups`) — purely a rebuildable derived cache. A
  `builderVersion` mismatch or missing/corrupt file both mean "rebuild",
  never "stale script."
- **`AudioScriptPipeline`** — orchestrates cache lookup, heuristic build, and
  opportunistic LLM refinement. `install()` (MAIN APP ONLY, via
  `Luna/AudioScriptPipelineWiring.swift`) observes `.readingListChanged`
  (debounced 1.5s) plus foreground/background transitions, and sweeps at
  launch: for every `.ready` readable article lacking a current-version
  cached script, builds the heuristic script synchronously (fast) and kicks
  off LLM refinement in the background if eligible (setting on, foreground,
  model available). `script(for:content:)` is the playback-time seam — cache
  hit returns immediately; cache miss builds the heuristic script
  synchronously as a last-resort fallback (the sweep is what normally keeps
  scripts ready ahead of time) and never blocks on the LLM. The Share/Action
  extensions never call `install()` — they never observe
  `.readingListChanged` or run the builder (extension memory limits +
  FoundationModels constraints); their scripts get built the next time the
  main app foregrounds.

### Extension audio (Phase 6)

The Share/Action extensions deliberately keep the LEGACY `SpeechController`
path (no `AudioPlaybackCenter`, no `AVAudioEngine`, no Now Playing/session
machinery — extension memory/lifetime rule out background audio entirely).
Phase 6 made that legacy path speak the TRIMMED script and gave the main app
a way to pick up where an extension left off.

- **What runs where.** The extension never calls `AudioScriptPipeline.
  install()` (no `.readingListChanged` sweep, no foreground/background
  tracking) — that stays main-app-only. Two small, extension-safe types in
  `LunaAudioPlayback` cover the extension's two touch points instead:
  - **`ExtensionAudioScriptWriter.writeHeuristicScriptIfNeeded`** — called
    from `LunaShareSurface.ShareSurfaceDriver.persistArticle` (the ONE
    canonical article-save completion point shared by the share and action
    extensions, regardless of whether the in-sheet reader opens). Writes a
    heuristics-only `AudioScriptCacheEnvelope` immediately (cheap/synchronous,
    off the ingest critical path) so the article is audio-ready before the
    main app's sweep ever reaches it. No-op if a script is already cached
    (never clobbers one the main app already refined).
  - **`ExtensionAudioScriptResolver`** — used by `ScrollReaderViewController`
    only on the legacy path (`ReaderAudioLauncher.center == nil`, i.e. only
    in an extension) when read-aloud starts. Resolves the best available
    script and feeds `SpeechController` its `spokenBlocks.map(\.blockIndex)`.
- **Degradation ladder (never blocks playback start).** Cached refined script
  > cached heuristic script > a freshly-built heuristic script (pure/fast,
  fine to run synchronously in-extension, and persisted immediately). If the
  resolved script isn't yet refined and hasn't permanently failed, an
  opportunistic on-device refinement pass is ALSO kicked off (subject to
  `AudioSettings.isIntelligentTrimmingEnabled` and `AudioTrimModelSession.
  isAvailable`, via the shared `AudioTrimModelSessionFactory.makeDefault()`),
  running while the extension stays open. On ANY error/unavailability it
  degrades silently to the heuristic script already in hand — exactly
  `AudioTrimIntelligence`'s existing error handling, reused unchanged. A
  completed refinement only WRITES THE CACHE for a later session; it never
  swaps the script an in-progress extension playback session is using
  (same hard contract as the main app's `AudioScriptPipeline.script(for:
  content:)`). `ExtensionAudioScriptResolver.cancelInFlightRefinement()` is
  called from `ScrollReaderViewController.deinit` so a straggling attempt
  never outlives the view controller that started it.
  FoundationModels inference itself runs out-of-process (a system daemon,
  not extension memory) and a web check turned up no documented prohibition
  against using it from an ordinary share/action extension (only
  MessageFilter extensions are called out as unsupported) — so the guarded,
  cancellable, silently-degrading attempt above is used as-is rather than
  skipped outright; `isAvailable` already folds every unavailability reason
  (Apple Intelligence off, unsupported language, model not ready, pre-iOS-26)
  into the same no-op path regardless of process type.
- **Block-index / highlighting mapping.** `SpeechController.init` takes an
  optional `spokenBlockIndices: Set<Int>?`; filtering happens via the
  file-scoped `speakableBlocks(content:spokenBlockIndices:)` (unit-tested
  directly in `SpeechControllerAudioTrimmingTests`, no `AVSpeechSynthesizer`
  needed). Each surviving entry keeps its ORIGINAL `content.blocks` index —
  `SpeechController` was already index-keyed rather than assuming a
  contiguous array (it already skipped empty-text blocks the same way), so
  every other method (`blockPosition(forAttributedLocation:)`,
  `willSpeakRangeOfSpeechString`) keeps mapping through
  `blockTextRanges[safe: block.blockIndex]` unmodified. The VISUAL reader
  (`content`/`rendered`/`wordMap`) stays untrimmed always — only which
  blocks are SPOKEN is restricted.
- **Handoff (extension → main-app), not true continuation.** The extension
  process dies on close (no background modes) — no responder-chain/openURL
  hacks are used. Instead, while the extension speaks, `SpeechController`'s
  existing position bookkeeping (see `ScrollReaderViewController`) persists
  through the SAME `AudioPlaybackPositionStore` format the main app already
  restores from (`AudioPlaybackPositionStore.Position` now also carries a
  `savedAt` timestamp, defaulted so pre-Phase-6 call sites/persisted data
  keep working unchanged). `AudioPlaybackCenter.restorableHandoffIfAvailable
  (now:)` is a NON-MUTATING peek (never touches `state`/the engine/the
  session) that returns an `AudioPlaybackHandoff` (title, thumbnail, word
  index, elapsed, a rough progress estimate) when idle AND a persisted
  position exists AND it's RECENT (`AudioPlaybackCenter.handoffRecencyWindow`
  — a named 30-minute constant) AND the item/its content still exist; nil
  otherwise (including "something is already playing"), which doubles as the
  "item deleted / content missing → do nothing" guard.
  `MiniPlayerHostViewController` checks this once at launch and, if non-nil,
  shows the bar in a paused preview — the center itself stays `.idle`, no
  half-initialized "paused but nothing built yet" state was added there.
  Tapping play routes through the EXISTING
  `restorePersistedSessionIfAvailable()` (reused, not duplicated); any real
  playback state arriving from that tap (or any other trigger) clears the
  preview flag so the ordinary `AudioPlaybackObserver`-driven display takes
  over.

### UI

- **`MiniPlayerHostViewController` + `AudioMiniPlayerView`**
  (`Luna/MiniPlayer/`) — window-level container `SceneDelegate` installs as
  `window.rootViewController`, wrapping the main `UINavigationController` as
  a child. **Luna Reader only** — read-aloud is a Reader-exclusive feature, so
  `makeMainRootViewController()` wraps in this host only when
  `AppSurfaceConfig.current == .reader`; the Downloader / Price Tracker apps
  install a bare nav controller (and skip `AudioPlaybackWiring.install()`
  entirely, so `ReaderAudioLauncher.center` stays nil there). Hidden while idle, animates in on first play, persists across
  push/pop; presented view controllers cover it (playback continues
  regardless). Content is layered as glass-siblings rather than inside
  `UIGlassEffect`'s contentView (layers there don't rasterize via
  `layer.render(in:)`). Contents: thumbnail, title, paragraph back/play-pause
  /paragraph forward/rate, autoplay toggle, `MoonHorizonProgressBar`. Tap
  anywhere else on the bar navigates to the playing article.
- **RSVP meld** (`AudioMiniPlayerMeld` in
  `LunaReaderUI/ReaderAudioLauncher.swift`) — when RSVP is frontmost in
  speech mode, it publishes its `controlsStack` as the anchor;
  `MiniPlayerHostViewController` observes `didChangeNotification` AND
  re-validates the anchor's actual on-screen visibility on every update tick
  (the RabbitHole host shows/hides pre-built children without appearance
  callbacks, so a stale anchor must fail the visibility check rather than
  rely on a clearing call) — the bar then slims down and docks above RSVP's
  circular controls.
- **`ReaderAudioLauncher`** (`LunaReaderUI/ReaderAudioLauncher.swift`) — the
  in-app/extension seam. `center: AudioPlaybackCenter?` is installed by the
  app shell (`AudioPlaybackWiring.install()`); when nil (Share/Action
  extensions) the shared readers (`ScrollReaderViewController`,
  `RSVPViewController`) fall back to the legacy self-contained
  `SpeechController`. `pauseIfPlaying(itemID:)` only pauses if the center
  already owns THAT item's playback — browsing another article never
  disturbs an in-progress one.
- **`AudioSettingsScreen`** (`Luna/Settings/AudioSettingsScreen.swift`) —
  "Audio" settings category: autoplay toggle, "Clean up articles for
  listening (Apple Intelligence)" toggle, enhanced-voice installation status,
  and the direct link to iOS's voice installer.

## Gotchas future changes must respect

- **Whole-block verbatim contract.** Trimming (heuristics or LLM) may only
  drop entire blocks, never edit text within a surviving block. Word events
  are computed against `SpokenBlock.text` and applied directly to the
  original `ArticleContent.Block.text` at the same `blockIndex` with no
  re-mapping — breaking this contract silently breaks reader word
  highlighting.
- **Remote commands are registered once, at launch, not lazily** — this is
  required for command delivery on a cold background relaunch (e.g. a
  lock-screen play tap after the app was killed). Don't move this into a
  lazy/on-first-play path.
- **Extensions keep `SpeechController`.** `ReaderAudioLauncher.center` is
  nil in the Share/Action extensions; nothing in `LunaReaderUI` may reach
  `AudioPlaybackCenter.shared` directly (that would instantiate the engine +
  session coordinator in a memory-constrained extension process). Same for
  `AudioScriptPipeline` — extensions never call `install()`. Phase 6's
  `ExtensionAudioScriptResolver`/`ExtensionAudioScriptWriter` reuse
  `AudioScriptStore`/`AudioTrimHeuristics`/`AudioTrimIntelligence` directly
  (cache I/O + pure/async trimming logic only) WITHOUT touching
  `AudioScriptPipeline`'s sweep/notification machinery — that distinction
  (which pieces of the trimming pipeline are extension-safe vs. main-app-only)
  is what makes trimmed extension playback possible without violating this
  gotcha.
- **iOS 26 availability guards around FoundationModels.** Despite this
  feature's plan doc historically describing the project as iOS 26+,
  `Luna.xcodeproj`'s actual `IPHONEOS_DEPLOYMENT_TARGET` is `18.0` on every
  target (and `LunaLibraries/Package.swift` declares `.iOS(.v18)`) —
  FoundationModels is iOS 26+-only, so every type that imports it
  (`AudioTrimIntelligence.swift`) is behind an explicit `@available(iOS
  26.0, *)`/`#available` check, and `FoundationModelsTrimSession` is only
  ever constructed behind one (`UnavailableTrimSession` stands in below iOS
  26, folding into the same "heuristics only" path as Apple-Intelligence-off
  or rate-limited).
- **Autoplay queue rule must mirror the displayed list exactly.**
  `AudioQueueRule.nextCandidate` reproduces `ReadingListSectioning`'s surface
  filter + `assignSections` + section order by hand (in `Luna/`, not the
  library, since `LunaAudioPlayback` can't depend on `ReadingListSectioning`)
  — if sectioning/ordering logic changes, this must be updated in lockstep or
  autoplay will queue an item the user doesn't see next.
- **Now Playing target ownership is adversarial with the legacy path** until
  the legacy path is fully retired: `SpeechController.teardownRemoteCommands()`
  calls `removeTarget(nil)`, wiping ALL targets on the shared
  `MPRemoteCommandCenter` including the new center's. `NowPlayingCoordinator`
  re-binds its targets every time `AudioPlaybackCenter` leaves `.idle` to
  reclaim ownership — don't remove that re-assertion while the legacy path
  still exists anywhere in-process.
- **Tone assets are checked-in binaries** (`Resources/ChimeTransition.caf`,
  `ChimeFinal.caf`) generated by `scripts/make_tones.py` — regenerate with
  that script rather than hand-editing/recording new ones, to keep the
  loudness/warmth spec (peak ~−12 dBFS, sine + gentle harmonics) consistent.
- **`ArticleAudioEngineTests` needs a real `AVAudioEngine.start()`** (even in
  manual/offline rendering mode) and can hang/crash the test host with a
  mediaserverd "RPC timeout, apparently deadlocked" abort on some hosts —
  seen consistently on one CI-adjacent Mac (macOS 27 beta + Xcode 27 beta +
  iOS 26.2 sim), reproducing across simulator reboot and sandbox toggling,
  while every other AVFoundation-touching test in the suite passed. Treat
  this as an environment/tooling flake to route around
  (`-skip-testing:LunaTests/ArticleAudioEngineTests` and verify that class
  separately/on another host) rather than a code regression — the class
  itself hasn't changed since Phase 1.

## Decisions log

- Neural TTS (Kokoro): **skipped entirely**; no pluggable-engine abstraction.
  Apple voices only.
- Queue: top-most readable article with `readState == .unopened`; if none,
  autoplay stops (final chime). `.opened` items are not auto-queued
  (explicitly chosen over the "include opened" variant).
- Browsing while playing: playback continues; explicit play switches.
- Announcements: same voice as narration, always 1.0× rate (pin time-pitch to
  1.0 for announcement segments).
- Trimming timing: build audio scripts opportunistically at save time (main
  app, `.readingListChanged` observer + launch/foreground sweep), NOT lazily
  at first playback — trimming often targets the very start of an article
  (byline/metadata), so a playback-time build would delay audio start.
- Trimming risk model: start/end trimming is less error-prone than
  mid-article trimming — edge runs may use weaker signals, middle removals
  need high-precision signals; removing a large fraction of total length is
  inherently risky — global ~50% cap with progressive degradation to
  conservative rule sets.

## Siri (Phase 7)

Saved articles are Siri/Shortcuts/Spotlight entities, and Siri can start
background read-aloud playback directly — no UI has to appear. Follows the
established App Intents split: `AppEntity`/`EntityQuery`/`AppIntent`
conformances live in the app shell (`Luna/Intents/`, for discovery); the
matching/ranking/selection logic they call into is plain, store-free,
unit-tested types in `LunaLibraries/Sources/LunaIntents/`.

- **`ArticleEntity`** (`Luna/Intents/ArticleEntity.swift`) — wraps a
  `ReadingListItem` restricted to `ArticleReadability.isReadableArticle`
  (`state == .ready && contentPlatform == nil && !isPriceTracker` — the same
  rule `AudioQueueRule.nextCandidate` uses for autoplay; never videos, social
  posts, or price trackers). Visible representation is title +
  "`<source host>` · `<date>`" (`ArticleEntity.subtitleText`, date-only when
  there's no real web host — e.g. a `lunadoc://` import). `@Property title
  /savedDate/sourceHost` so Shortcuts' Find/filter actions work. Conforms to
  `IndexedEntity` (iOS 18+; `attributeSet`/`hideInSpotlight` use the SDK's
  default implementation — no custom attribute set needed for this use case).
- **`ArticleEntityQuery`** (same file) — `EntityQuery.entities(for:)` (by id),
  `EntityStringQuery.entities(matching:)` (the "find" workhorse), and
  `suggestedEntities()` (recent unread articles, ~10). All matching lives in
  `LunaIntents.ArticleMatcher`; the query type only bridges it to
  `ReadingListStore`.
- **`LunaIntents.ArticleMatcher`** — pure functions over `[ReadingListItem]`,
  never loading `ArticleContent` (title/host/url only, so it's cheap over a
  large list):
  - `search(query:in:now:calendar:limit:)` — the string-query workhorse.
    `ArticleQueryParser` splits the query into an optional relative-date
    filter (`ArticleRelativeDateFilter`: `.today`/`.yesterday`/`.thisWeek`,
    matched via longest-phrase-first scanning so "this week" doesn't leave a
    stray "week" token) and the remaining free-text tokens. Each candidate is
    scored by token overlap against the title (×2) and the source (×3 — host
    + `ArticleSourceName.humanReadable`, e.g. `"theatlantic.com"` →
    `"the atlantic"`, so "from The Atlantic" matches); ties (and pure
    date-only queries like "yesterday") break by recency, which is also what
    makes "latest … from X" phrasing fall out naturally rather than needing
    separate handling.
  - `suggested(in:limit:)` — unread readable articles, newest first.
  - `latestUnread(in:)` — newest-saved unread readable article, the
    nil-entity fallback below.
- **`ReadArticleIntent`** (`Luna/Intents/ReadArticleIntent.swift`) — conforms
  to **`AudioPlaybackIntent`**, verified directly against the installed
  AppIntents SDK swiftinterface: `public protocol AudioPlaybackIntent:
  SystemIntent` (`SystemIntent: AppIntent`) — a marker refinement with NO
  extra required members beyond `AppIntent` itself, available iOS 17+. It
  tells the system to run `perform()` in the app's own process and allows
  starting audio playback without foregrounding. `openAppWhenRun = false` is
  kept anyway (harmless, matches every other intent's convention). Optional
  `article: ArticleEntity?` parameter: provided → play it (re-validated as
  still readable); nil → `ArticleMatcher.latestUnread`. Loads the item's
  `ArticleContent` from `ReadingListStore` and calls the SAME
  `AudioPlaybackCenter.shared.play(item:content:)` the in-app mini-player
  uses — `AudioPlaybackWiring.install()` runs in `AppDelegate.
  didFinishLaunching`, before any intent could plausibly run, so the center
  is always wired. Dialog: `"Reading <title>."`; throws a localized error for
  no-unread-articles or missing content.
- **`LunaShortcuts`** (`AppShortcutsProvider`) gained a 10th `AppShortcut`
  (the provider's documented hard cap — see `claudedocs/app-intents.md`) with
  7 phrase variants covering all three utterance families: bare/"latest"
  ("Read/Play my `\(.applicationName)` article[, latest]") and
  entity-parameterized "about `$article`"/"from `$article`" variants (both
  "Read" and "Play").
- **`ArticleSpotlightIndexWiring`** (`Luna/ArticleSpotlightIndexWiring.swift`,
  installed at launch right after `AudioScriptPipelineWiring`, main-app-only
  like the trimming pipeline) — sweeps on launch and on debounced (1.5s)
  `.readingListChanged`: builds a `CSSearchableItem` per readable article from
  `ArticleEntity.attributeSet`, calls `associateAppEntity` (so Spotlight's
  semantic index can resolve back to the entity/intent), indexes them via
  `CSSearchableIndex.default()`, and deletes entries for ids that dropped out
  of the readable set since the last sweep (a small id-set diff persisted in
  App-Group `UserDefaults`, so a deletion that happened while the app was
  terminated is still cleaned up on the next launch).

### Known limits (honest accounting)

- **Date-phrase resolution is the speculative part.** Siri filling the
  `$article` entity-search-string parameter with "yesterday" out of "Read my
  `\(.applicationName)` article from yesterday" is standard `EntityStringQuery`
  usage, but whether Siri's NL parser actually segments THAT phrasing that way
  (vs. failing to parse the sentence at all) can only be confirmed on-device —
  there is no headless way to exercise real Siri intent resolution.
  "About Boston"/"from The Atlantic" (an explicit noun-phrase content slot)
  are much more standard Shortcuts patterns and are expected to resolve
  reliably; "yesterday" is the honest reach.
- **Source-name matching is heuristic**, not NLP word segmentation:
  `ArticleSourceName.humanReadable` only special-cases a leading "the" run-in
  (`"theatlantic"` → `"the atlantic"`) and dot/hyphen splits — a smushed
  compound host with no "the" prefix and no separators (e.g. `"nytimes.com"`)
  stays as one token (`"nytimes"`), so "from The New York Times" only matches
  it via the host token itself, not word-by-word.
- **No content-body matching.** Per the design constraint, `ArticleMatcher`
  never loads `ArticleContent` for a query — "about Boston" only matches if
  "Boston" is in the article's TITLE, not its body text.

## Manual verification still needed (device, not simulator)

Background audio, AirPods press-to-resume, lock-screen scrub, and
interruption/route-change behavior are exercised by unit tests against the
protocol seams (`AudioSessionCoordinator.Action`, `RemoteCommandBinding`), but
the real system behavior can only be confirmed on a physical device. See the
Phase 5 integration report's punch-list.

### Siri punch list (device only)

- "Read my latest `<app>` article" — should start background audio for the
  newest unread readable article with no UI appearing.
- "Read my `<app>` article about Boston" / "…from The Atlantic" — should
  resolve the right `ArticleEntity` via Siri (not just `ArticleMatcher`
  in isolation) and start playback.
- "Read my `<app>` article from yesterday" — the speculative one; confirm
  whether Siri actually parses "yesterday" into the `$article` slot at all,
  and if not, note the failure mode (falls through to a full-text search of
  the literal word "yesterday", which would only work if that word is in a
  title).
- Spotlight: saved readable articles show up in system search; deleting/
  reading an article updates/removes its Spotlight entry (`CSSearchableIndex`
  writes are async — allow a beat).
- Confirm the 10th `AppShortcut` didn't push `LunaShortcuts.appShortcuts`
  over the provider's hard cap (`appintentsmetadataprocessor` build error if
  so — see `claudedocs/app-intents.md`).
